Weekend build plan v1.3: Postgres queue, direct Claude API, CSV export, built with Claude Code. Working slice by Sunday 13 September, 22:00 ET
Version 1.3, Friday 11 September 2026, revised after the scope decision taken this afternoon: review and approval live in Postgres for the whole pilot, not just the weekend, and approved records leave as a CSV export BD imports into Zoho. Supersedes v1.1 and the file circulated as v1.2. Prepared by Ryan Dear. Companion to Pilot Plan v0.4 and Technology and Architecture v0.4. Working document.
1. Verdict
By Sunday night the Monitor can be functional in the only sense that matters for Monday: real notices from four live feeds (TED, Prozorro, Find a Tender, World Bank) flow every hour through change detection, the free filter, Claude scoring and dedupe into a review queue held in Postgres and served by a small review app on the same host, one click by a named reviewer writes an Opportunity-shaped row to approved_records, and one command produces the CSV file BD would import into Zoho, with a manifest and a full audit trail behind it. The checkpoint is enforced in the database: the pipeline's database role cannot write to approved_records, only the review app's role can. That is increment 1 of the architecture plus three feeds and the export, running on a single host.
What changed from v1.1. The review app and the Postgres store are no longer a weekend stand-in for a Zoho build in weeks 1 to 3. They are the pilot. There is no Zoho work in any of the fourteen weeks, and the CSV export replaces the integration entirely. Two practical effects on the weekend: the table is named approved_records rather than crm_leads, because nothing has been built yet and the rename is free today and stops the name implying an integration that does not exist; and a thin export is added to Sunday evening, because a file BD can look at is a much better Monday than a database row I describe.
What "functional by the weekend" does not mean, and I will not pretend otherwise: no West African portal connectors, no translation stage on live data (it is built, but the four weekend feeds carry English titles or CPV codes so it is not exercised), no Terraform, no notifications, no scheduler hardening beyond hourly timers. Those are week 1 to 8 work in the pilot plan and stay there. A weekend that tries to do them produces nothing that works.
The plan below is sequenced so that at every gate there is something demonstrable. If Saturday goes badly, Sunday still ends with TED notices scored in a queue. If Sunday goes badly, Monday's demo runs from the database and the existing simulation, and no one has lost the build.
The weekend has two dependencies left, both in my hands tonight: an Anthropic API key under the approval, and a machine with Docker.

3. Definition of done for Sunday 22:00
CLAUDE.md and BUILD_ORDER.md exist, are committed as the first commit, and every Claude Code session reads them.
Four feed connectors run on a schedule (hourly during the weekend so progress is visible; daily in the pilot) with fixtures recorded for each.
Every notice is stored in its original form, hashed, and never processed twice.
The CPV and English lexicon filter drops the bulk of TED volume before any model call; the drop rate is reported per source.
Claude Haiku 4.5 returns a schema-valid score for every survivor; schema validity is measured; failures are retried once and parked.
Duplicates across sources (a World Bank notice and its TED mirror, for example) cluster into one candidate.
Candidates at or above the threshold appear in the review app with title, score, matched functions, summary, links, original text where the language is not English, and the proposed record rendered field by field.
Approve, Edit-then-approve and Reject-with-reason work; Approve inserts an approved_records row with the reviewer's name; the pipeline database role has no privilege on that table, proven by a test that tries and fails.
One command produces a UTF-8 CSV with a BOM and a sibling manifest, writes exported_at and export_batch back onto the rows, and refuses to export the same batch twice.
Every transition is in the audit log with actor, before and after.
A one-page runbook exists: how to run, how to add a source, how to read the health table, how to export, how to stop it.
A ten-minute demo path is written down and rehearsed once.

8. Bedrock: when, and why not now
Direct API now is the right call and I would not bring Bedrock forward. Functionally the two routes are the same models, the same SDK and the same prompts; the only code difference is the client class. What Bedrock buys is governance and billing, not capability: the calls land on the existing AWS invoice under the existing AWS agreement, the data stays in ca-central-1, and the CEO sign-off reads better. None of that matters while the pipeline is running on fixtures and public feeds in shadow mode.
Cut over at whichever comes first: the governance approval is written up and names Bedrock as the route, or entry to live mode in week 11, when the system becomes something the company relies on. The cutover is half a day: enable model access in the member account, swap Anthropic() for AnthropicBedrock(), re-run the golden set to confirm identical scores at the same prompt_version, and record it in the decision register (D1). Keep the direct key alive for two weeks after as the recorded alternative, then revoke it.
Two reasons to cut over sooner: the direct API key ends up on a personal rather than a company account (move to Bedrock immediately, or at least to an organisation-owned key with a spend limit), or Haiku 4.5 and Sonnet 5 turn out not to be served in ca-central-1 and a cross-region decision has to be taken before the residency line goes into any governance paper.
